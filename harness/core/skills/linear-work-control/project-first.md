# Project-first intake and execution

Team is the stable organization/workflow boundary. Project is the product/delivery-stream boundary. Several products may share a Team; different products must not silently claim the same Project UUID. Labels describe workstream, executor and runtime attention; status describes lifecycle. None grants permission or filesystem isolation.

## Automatic tracked intake

In an adopted repository (`.harness/linear/routing.json`), every new tracked task enrolls in Linear by default, including direct execution without ChiefOps. Quick work stays exempt. A user explicitly asking a new local project to use Linear day/night management authorizes scoped bootstrap; folder discovery alone does not. Explicit opt-out remains local-only.

## Workspace selection and multiple workspaces

`workspaceId` is the durable workspace identity. `workspaceSlug` and URLs are compatibility and display fields, so a rename or URL change updates those projections without changing Team, Project, issue, or Trio identity. Each adopted repository keeps one explicit expected workspace profile in its local routing policy.

Normal intake does not require the operator to assign a workspace on every task. The harness reads the authenticated Linear workspace before each read, claim, or write and compares its ID (and, where available, normalized slug) with the repository policy. A mismatch returns `workspace-selection-needed`/`setup-needed` and stops the mutation; it never guesses from a Team, Project name, folder, or issue title.

When a new repository is enrolled, or when work moves to another workspace, perform one explicit enrollment/rebind and authenticate the Linear connection to that workspace. After that, normal intake, day/night routing, and Project assignment are automatic within that repository profile. The current Linear connector exposes one authenticated current workspace and does not accept a workspace argument on each MCP write, so it cannot silently switch between multiple workspaces in one connection. Supporting concurrent automatic switching requires host-side connection profiles; until then, re-authenticate or select the intended connection once and let the guard verify it.

1. Read the bound Trio, authenticated workspace, repository Git root/common-dir and routing policy. Never copy another repository's policy. A missing policy during requested enrollment means `setup-needed`, not silent optional tracking. Safe local work may continue; no unattended claim until enrollment succeeds.
2. Bootstrap only when requested: use the approved existing Team, paginate Projects and read full descriptions looking for exact `productKey: <key>; projectKey: <key>` ownership markers. Reuse one verified match, create a default Project for zero matches, reject multiple or conflicting ownership. Check Team membership and target workspace. Do not auto-create Teams, upgrade plans, rename unrelated Projects, or restore closed Projects. Record returned UUIDs only after readback, with policy root independently measured from Git. No global scheduler/registry is introduced.
3. Validate project ownership across the adopted configurations available for this enrollment; pass those policies as `registryPolicies` to the helper. Unknown other repositories are coverage unknown, not proof of global uniqueness. Do not select a Project already marked for another product.
4. Run `scripts/project-routing.mjs plan-intake` from this skill directory with a complete, fresh snapshot. Record pagination completion, full configured-Project descriptions/ownership markers and fully-read issue/marker coverage in existing progress evidence; set `complete`, `paginationComplete`, and `markerSearchComplete` only after all pages and relevant candidates are exhausted. Also supply `projectOwnershipComplete: true` and the fully-read workspace-wide `projectCatalog` (including archived Projects); duplicate ownership markers outside the configured Project set deny intake. Missing/partial/unknown coverage means `coverage-unknown` / `setup-needed`, never an empty queue or zero-match create. Exact binding/parent/project key must agree; otherwise reject. A new task without an explicit stream uses this product's default Project. Use exact marker `harness-task: <productKey>/<taskId>` (slices add `/sliceKey`) on its own line inside a fenced `text` code block in the issue description. Fencing prevents Linear auto-linking identifiers such as `sup-15` and changing the marker; legacy unfenced exact markers remain readable and eligible after exact fresh readback; fencing is a write-format requirement, not a reason to invalidate stable identity. Parse all marker lines from full descriptions, reject duplicate/malformed/conflicting markers and read back the literal line. Paginate and fully read marker candidates before declaring zero matches. Existing bound legacy tasks keep UUID identity; read their existing marker or add one with guarded readback before marker-based reuse or unattended admission. The marker derives from the bound taskId and slice key, not an issue title or guessed product. Marker-less legacy tasks remain recoverable for guarded backfill, but cannot enter unattended execution until exact marker readback succeeds. Never match by title alone. `planOnly` is not creation or authorization.
5. Execute the proposed MCP create/reuse only after workspace and destination checks. Preserve issue state on reuse; new work starts Backlog until scope, dependencies and authorization are ready. Record issue UUID, Project UUID, Team UUID, Trio path and a comment verified to belong to that issue in the existing binding format. Keep v1 maps lossless; do not flatten parent/children into one v2 issue. A lost response requires re-reading by marker before retry; failures become explicit sync debt.
6. Map ready work to Todo + agent-ready. Add nightly only when unattended execution is authorized and dependencies, root and concurrency checks pass. Review maps to In Review + ready-review; Done requires the completion gate. Parent In Progress is not worker activity. Keep non-runtime labels intact.

## Every read/claim/write boundary

- Continue using workspace `guard`; additionally run `scripts/project-routing.mjs guard-target --repo <current-root>` with the policy, normalized exact binding and fresh full issue. The expected Project is the task's Project, not merely any allowed Project. Comment writes pass expected comment ID and observed comment ownership. For creates, use verified Project state/team/workspace from `plan-intake` before mutation and guard the returned issue after it.
- Normalize v1 goal/taskMap/subIssues/subIssueIds and v2 task-binding using `scripts/project-routing.mjs normalize-binding` (shared `lib/project-binding-normalize.mjs`) with an explicit task/slice selector and fully-read normalized issue inventory. `selected.expected` is the input to `guard-target`; `mappings` retains all children. `markerReady=false` permits identity recovery/backfill only. Reject ambiguity; do not assign a parent status comment to a child. v1 retained within its explicitly registered product is compatibility, not blanket multi-product permission. For v2 use `resolve-product-binding`; do not feed v2 to v1-only `resume-brief`.
- A manually moved issue denies the next write until an authorized local rebind. Post-write readback detects drift but is not a transaction. Same repository/worktree family always shares its concurrency boundary across Projects. Use an available lock; conflicting/unknown ownership defers writes. Project/status claims are not locks.
- Night/morning discover all current-repository bindings and query each exact Project, deduplicate UUIDs and retain a single global attempt/time budget. Never query the entire shared Team as an executable queue. Unknown project/issue reads are coverage gaps. Group human summaries by Project and show the next action/reason.
- The helper consumes caller-supplied authenticated snapshots. Tests prove deterministic validation, not immunity from agents bypassing the protocol or future Host success. Keep configured, implemented and observed-run evidence separate.

## Caller sequence and evidence limits

`resume-brief` is read-only preparation, not a Project guard or execution permit. All adopted callers follow: normalize exact binding → verify complete fresh inventory and ownership → verify marker readiness / plan intake → workspace guard → exact target guard → one authorized MCP mutation → fresh identity/comment readback. Creating a comment has no existing comment ID; guard the issue first, then read the new comment from that issue before storing its ID. Editing a comment requires the existing expected comment ID and matching freshly read issue ownership.

CLI helpers validate supplied evidence; they do not intercept arbitrary MCP calls. Chief/direct/night/morning policy mandates this sequence. A Host-enforced interceptor and atomic cross-process locks are not claimed by this implementation.

## Lifecycle and new products

Follow [lifecycle.md](lifecycle.md) immediately after close/archive/reopen. Use the bootstrap-project helper for requested enrollment: one default main Project per new product, preserving an existing policy default. Additional streams require an explicit stable key and independent delivery scope. Codex project entries and multiple Trios never trigger additional Projects.
