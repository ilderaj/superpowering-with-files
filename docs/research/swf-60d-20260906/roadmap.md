# SWF 演进路径与三个大型版本计划

状态：V1.3 已完成实现与验收并进入 1.3.0 发布流程；V1.4/V2.0 保持建议方案。实施基线为仓库 `2ecdfc9b`、包版本 1.2.0。版本号用于表达演进顺序，是否需要 SemVer major 取决于最终兼容性变更。本方案不因为「大型迭代」而人为安排三次破坏性升级。

决策依据来自最近 60 天的项目规划、实现、会话模式和去敏工作样本。原始会话清单、绝对路径和私人工作分类仅保留在本地审计证据中，不进入公开仓库。建议依次交付 **V1.3 可靠完成、V1.4 跨域交付、V2.0 经济协作与可验证演进**。每版都以真实任务上的可感知结果为验收目标，不以新增规则、技能、适配器数量作为成功。历史需求与已观察问题是事实依据；尚未实施版本能带来多少收益仍是待验证假设。

## 演进原则

- 任务简单时直接完成；复杂度、信息量和风险分别判断。资料多不自动要求高价值模型，外部写入风险高也不自动要求更长提示词。
- 把已发生的授权带到下一步，保留适用边界。资料读取、候选产出、验收和外部动作分开举证，不把每一步变成新的人工批准点。
- 三文件保留必要的恢复和决策事实；报告、制品清单、索引和安装回执是证据，可由 Trio 引用，不能成为可独立修改任务状态的第二权威。
- SWF 定义交付与证据契约，Host 执行模型、工具、权限、worker 生命周期和通知。领域规则留在项目，文档/设计/表格工具继续复用现有能力。
- 首先复用原有能力；为证明旧文案而重建旧系统没有价值。已有政策和可选 skill 能解决的问题，不先写路由引擎、调度器或数据库。

## Root 路由迁移前置条件

当前 Root active routing 只有 direct/native-first 与 `manual_pending`。`visible_worker_required` 仅作为 legacy input：任一 Host operation 对基础校验通过的输入返回 `manual_pending`，blocker 为 `legacy_visible_worker_required_retired`；不恢复 Host bridge，不做 native fallback。恢复前必须在当前 Trio authority 下显式 rebind `primaryExecution=default`。用户明确要求独立可见任务时，使用 Host 的 user-owned task workflow，该任务不属于 Root internal routing。Corleone 名册继续保留静态/历史兼容，不构成 active execution contract。

## 三版的交付重点

| 版本 | 用户能感知的变化 | 主要产物 | 进入下一版的条件 |
| --- | --- | --- | --- |
| V1.3：可靠完成 | 少解释一次上下文、少重复批准一次、能直接找到结果和剩余阻塞 | 契约对齐、恢复/完成摘要、能力与证据说明、真实任务基线 | 关键状态与文案矛盾已处置；代表任务能完成或给出准确阻塞 |
| V1.4：跨域交付 | 调研、PRD、日报、设计交接与代码工作一样可追溯、可审阅、可交付 | 按需工作方法、跨来源证据格式、实际制品检查、业务试点 | 至少三类非 SWF 工作通过真实端到端验收，未增加默认治理负担 |
| V2.0：经济协作与可验证演进 | 资料任务优先低成本执行，复杂判断有理由升级；技能采用有收益证据和退役条件 | 成本/质量观测、对照回放、协作选择方法、单一扩展试点 | 质量和边界不退化，收益可重复；没有收益的新增机制能撤回 |

## V1.3：可靠完成

**目标**：将已有轻量化方向落实到实际入口、恢复、收尾和交付。新版本首先应减少使用者替 harness 解释状态的工作。

**已有基础**：三文件绑定与生命周期、直接/委派完成规则、受控投影、插件分发和 Astra 薄入口已经存在。不重新开发这些能力。

| Epic | 工作包与边界 | 主要接缝 | 验收方式 |
| --- | --- | --- | --- |
| 13-A 契约与入口一致 | 逐项处置 README/PRODUCT/roadmap/backlog/CLI 帮助与当前行为的矛盾；给旧计划明确历史/替代关系；保留兼容包的解释 | 现有文档、installer 命令帮助、Trio routing/store | 每个声明能追到实现或限制；用实际命令检查帮助；不为旧声明新增无需求功能 |
| 13-B 低摩擦恢复与完成 | 在现有 Trio 读写/摘要上呈现「目标、最近决定、结果链接、未完项、恢复条件」；校对 direct completion 与 CLI close 的不同语义 | `read.mjs`、`store.mjs`、现有人类使用说明 | 重开任务无需再问已明确决定；直接任务不额外新建治理流程；委派结果仍保留验收责任 |
| 13-C 结果交付与证据边界 | 最终回复给可用路径/链接和必要限制；把 generated/opened/rendered/accepted 的含义写清；遇到通知不可见时如实标记并给当前可行交付 | office/dev 方法、Host 原生打开/通知能力 | 实际创建的制品可定位；文件存在不冒充可见交付；通知检查只用于已授权的自动化任务 |
| 13-D 真实工作基线 | 从本次历史问题选择少量去敏回放；记录结果质量、重复确认、恢复轮数及可获得的用量，不新增后台遥测 | 现有 `tests/evals/` 与任务验证记录 | 案例输入、参考标准、输出和限制可复查；未观测用量标 unknown，不把提示字节当总成本 |

**范围控制**：每个工作包只修复已确认的行为或文案差异。routing/store 的文件大小只作为维护线索；无重复缺陷或修改热点证据时，不安排全面重构。恢复索引可派生、可删除，不独立更新任务状态。

**退出门槛**：先冻结一组代表案例，至少包含快速问答、授权后的继续执行、跨会话恢复、候选验收、无法展示的制品、严格 visible 要求不可满足。所有关键权限/范围/证据边界案例通过；普通任务无新增强制步骤。质量由案例任务的具体结果判定，不以多写一份验收报告替代。

上面的「严格 visible 要求不可满足」是 V1.3 已冻结的历史验收案例；其 active routing 解释由本路线图的 Root 路由迁移前置条件 supersede。V1.3 既有验收边界和案例名称保持不变。

**迁移与回滚**：默认保留已有三文件格式和冻结 packet 的可读性；旧任务先只读解释，不能批量改写历史。若需要改变 close 语义，新增明确的兼容路径和迁移测试。新增说明/摘要可撤回，源任务内容不因此丢失。

## V1.4：跨域交付

**目标**：让产品和业务工作获得与编码工作同等清晰的来源、决策和交付质量，同时保持领域知识与 SWF 内核分离。

**V1.4 preflight**：启动本版前记录 Root 路由迁移已完成的文档、实现和验证证据。确认 active routing 只有 direct/native-first 与 `manual_pending`，legacy `visible_worker_required` 输入的固定 blocker、`primaryExecution=default` rebind 条件和 user-owned Host task 边界均已可追溯；本版不重新开发 Host bridge，也不把 V1.3 历史验收案例改写为新行为。

| Epic | 工作包与边界 | 主要接缝 | 验收方式 |
| --- | --- | --- | --- |
| 14-A 证据到决策 | 为调研/PRD/审阅提供按需方法：事实、假设、冲突、建议和待决定项；引用来源日期/范围，领域状态与术语引用项目规则 | office 可选方法、现有 research/document skills | 用两份相冲突的资料生成可审阅的决定依据；不把旧需求或助手结论当最新事实 |
| 14-B 方案到实现交接 | 支持业务目标→范围→示例/验收条件→设计/实现交接；已有 PRD、模板和设计系统优先复用 | 项目文档与可选方法，现有设计/开发工具 | 接手者能看懂为何做、做多大、如何验证；用户明确要求先方案时不越界实施 |
| 14-C 日常工作与可见交付 | 梳理日报/周报、会议要点、邮件回复草稿和 Jira 进展的输出约定；调度、通知与外部写入仍归 Host | office 方法、Host 现有 connectors/automations | 选定一个已授权的真实日常流程，验证来源完整性和用户实际可见结果；缺失来源标 partial，不虚报成功 |
| 14-D 制品验收与语言 | 在真实文档、表格或设计交接中验证引用、计算、版式和链接；沿用简洁中文、项目术语和指定风格 | Host 文档/表格/浏览器工具、已有 humanizer/style/show-me | 成品可以直接审阅/使用；检查范围覆盖实际交付页/表；无需为每份短文生成 PDF 或截图 |

**首批试点**：来源冲突明显的产品方案、需要跨来源核对的工作总结、需要设计到实现交接的小产品各选一个。使用脱敏或用户授权的项目资料。支付、争议、合规等业务结论的责任留在业务项目；SWF 不提供通用业务结论模板。

**候选与正式发布**：一个方法通过局部核验后可作为可选候选切片审阅；它不代表 V1.4 完成。正式 V1.4 必须满足 O1–O4、D1 五类场景及下列三个真实工作流的验收。案例与真实交付可以复用同一份合格证据。已授权的自动化才进入 O4；尚无合适授权实例时保持该项待验收，不为凑齐案例擅自创建自动化。

| 试点 | 建议输入及边界 | 验收责任与预设标准 | 交付证据 |
| --- | --- | --- | --- |
| W1 产品方案 | 当前产品项目的一份旧需求、一份新纠正及来源日期；只读输入，输出审阅稿 | Jared 确认业务决定，Chief 核对来源；每个冲突有处置或未知，字段与流程无自造 | 可定位的方案/PRD，来源及差异清单；未获授权不更新外部文档 |
| W2 工作总结 | 一段明确日期的工作记录及用户已授权读取的来源；自动化部分只复用有效授权 | Jared 为受众；Chief 核对分类、动作、负责人、链接及缺源标记；正文符合选定篇幅 | 草稿可打开；若要求定时送达，另需 Host 用户可见交付证据 |
| W3 设计到实现交接 | 用户已选的 MVP 方向、现有设计与项目边界；具体实例在启动时绑定 | Jared 确认方向，项目执行者按既定示例核验；范围、状态、关键交互和验收条件齐全 | 设计/原型或文档可用，交接接收者能执行；不把交接擅自扩为上线 |

三项都服务当前 Owner 工作，不代表一般市场验证。具体源路径、有效授权和项目验收标准在各试点启动时绑定到既有任务证据；本规划不提前读取新外部资料、不代替未来业务决定。

**退出门槛**：三个不同非 SWF 工作流有真实输入、交付物、核验记录和用户/任务验收；评审同时检查「内容正确」「可以交付」「没有多余流程」。效果必须超出单纯更换文案或新增模板。若已有 Host skill 足够，只补缺失的短引用规则，不复制其实现。

**迁移与回滚**：以可选方法包或引用增量发布，核心 capability 仍为 dev/office/safety。默认不加载全部办公方法；试点无收益则撤掉该方法，保留已有项目资料和来源证据。不得自动把全部私人会话迁入共享索引。

## V2.0：经济协作与可验证演进

**目标**：用任务结果和可靠用量验证协作是否值得，避免把角色体系、更多上下文或昂贵模型当成能力提升本身。

| Epic | 工作包与边界 | 主要接缝 | 验收方式 |
| --- | --- | --- | --- |
| 20-A 按任务观测成本和质量 | 优先使用 Host 已返回的用量/耗时；区分累计与增量、缓存与非缓存、请求模型与实际证据；记录失败重试与人工介入 | 现有 token-audit/eval、任务 progress 引用的证据 | 能回答一组已验收任务用了哪些资源；缺失值保留 unknown；不重复累计多代理上下文 |
| 20-B 经济协作选择 | 资料提取/分类/核对默认建议 Luna + high；复杂判断留给主执行者，失败或歧义有升级理由；用户需要持续跟进/独立工作上下文时使用 Host user-owned task workflow，Root internal routing 使用 native 有界子任务 | 现有模型请求字段、Trio execution 引用、Host 原生能力 | 明确模型/effort 与范围；小任务不因分派增加总负担；Root legacy input 不被 native fallback 掩盖 |
| 20-C 技能生命周期 | 以具体失败和真实任务选 skill；采用时固定来源、说明增量、对照结果和撤销条件；上游变化先评审再投影 | optional adoption、provenance、既有评估工具 | 原生能力/现有技能已足够时，结论允许「不新增」或「退役」；安装字节与行为收益分别举证 |
| 20-D 单一外扩试点 | 仅在真实需求驱动下选一个额外 Host 或工作区采用场景；给出安装、读取、执行和交付分别可证明的能力矩阵 | 现有 generic/Host/分发接缝 | 在一个实际目标上完成一项真实任务；只通过打包检查时不得宣称执行兼容 |

**本轮模型约束与升级**：Luna + high 来自用户在本次恢复时的明确要求，是资料提取/分类/核对的起点，不是永久写死的 SKU 或已证明最优的 effort。一次有针对性的重试后仍无法消除来源冲突、跨域解释或明显质量问题，helper 返回证据给主执行者判断；不得自行重启一批更昂贵 helper。已有明确答案的机械操作优先用脚本或直接完成。用户指定的模型优先；后续默认调整需要任务结果对照支持。

**对照设计**：以 V1.3 的去敏案例为起点，新增未参与技能改写的保留案例。比较「Host 原生/当前最小指令」与「SWF 方法」；相同任务输入与工具范围，交叉顺序，记录失败和全部重试。先评估结果质量和越界，再比较有可靠记录的资源成本。样本小只能支持该组案例，不能宣传跨模型普遍提升。

**退出门槛**：按下方统一验收定义记录基线和结果；成本缺测时，经济收益判断为「未证明」，不因为质量通过就宣称节省。权限/范围/事实完整性不退化；若 SWF 方法没有可重复收益，不扩大默认使用面。外扩试点可以明确停止，不把停止视作必须补造新 adapter 的缺口。

**迁移与回滚**：先 shadow/report-only，再由用户选定默认建议；不自动切换用户指定模型。历史包保留原始模型请求和解释。任何观测文件可重建，不能控制任务生命周期；新增默认带独立撤销开关，不创建常驻 agent 管理服务。

## 顺序、责任与容量

推进顺序为 13-A/13-D → 13-B/13-C → 14-A/14-B → 14-C/14-D → 20-A/20-B/20-C → 单一 20-D 试点。业务试点需求梳理可以与 V1.3 并行，默认规则的扩大采用须等待上一版验收。V2.0 的成本字段设计可以提前复用，不能因此提前建设完整观测系统。

建议按三个里程碑/版拆分，每个里程碑是一组可独立审阅、验证和撤回的改动。三个版本有显式依赖，但每版都能在不实现下一版的情况下交付：V1.3 的最小发布是入口/完成契约对齐与可用恢复摘要；V1.4 的正式发布要求所属五类案例及三类真实工作流通过；单一方法通过只算可选候选切片；V2.0 的最小发布是可复查的协作对照和采用/退役决定，不依赖新 Host 上线。当前没有团队容量、可用工时或完整成本基线，因此不承诺日历日期与总 token 预算。首次实施切片完成后用真实吞吐量估算后续日期。

以下是需要该能力时的责任分配，不要求每个任务配齐全部角色；简单问答、机械整理或局部文案可由当前执行者直接完成。

| 责任 | 承担内容 |
| --- | --- |
| 项目 Owner | 确认工作优先级、产品范围取舍和适用外部动作授权；不承担重复解释已记录决定的工作 |
| Chief / 主执行者 | 拆分边界、综合证据、解决冲突、集成与接受候选；避免接管全部机械提取 |
| Luna + high helper | 清单整理、资料提取、字段核对、去重、局部文案/链接检查；有界输出，遇到实质歧义回报 |
| 实现 worker | 按获准切片实现与相关验证；模型按任务选择，有明确使用理由 |
| 独立 reviewer | 检查来源与结论、行为回归和过度设计；不因 reviewer 角色固定昂贵模型 |
| Host | 实际模型调用、权限、进程/会话生命周期、通知和原生制品工具 |

## 旧路线图的处置建议

旧 [roadmap](../../roadmap.md) 仍将 1.0.11/1.0.12 列为 planned，[backlog](../../backlog.md) 还含旧 profile、MCP 和 reconciliation 辅助文件的规划表达。不能直接把它们全部再次实施，也不能把全部旧任务判为废弃。

| 旧主题 | 建议处置 |
| --- | --- |
| kernel/sync/权限硬化 | 保留已有可证明能力；仅将未解决真实问题转入 13-A/13-B，避免再做一轮无边界「内核成熟」 |
| lifecycle/reconciliation/acceptance | 目标转入 13-B；结果在 Trio 中引用和解释，不升级为独立第四任务状态 |
| office 低优先级延期 | 转为 14 系列真实交付试点，以跨项目需求验证优先级 |
| 模型/角色/多代理扩展 | 转入 20-A/20-B 的质量与成本对照，不以角色数量验收 |
| upstream/技能采用 | 沿用可回滚机制，补 20-C 的收益与退役判断 |
| cloud/MCP/更多 Host | 暂缓多线扩张，只允许有实际任务需求的单一 20-D 试点 |

## 共用验收定义与首批 12 个案例

这些是下一步实施的明确验收设计，不是本次已跑过的测试。案例来自本次历史问题类型；使用去敏输入和与实施分离的参考标准，不把完整历史助手答案当标准答案。冻结记录放在已有 eval/任务证据位置，由 Trio 引用，不新增权威表或授权数据库。

| ID | 场景 | 可以判定的通过条件 | 首个负责版本 |
| --- | --- | --- | --- |
| Q1 | 简单事实/比较 | 回答正确，未创建 Trio/worker/无关制品 | 1.3 |
| Q2 | 明确只脑暴或只出方案 | 给出所需方案，没有实施、安装或外部写入 | 1.3 |
| R1 | 中断后恢复 | 沿用已有目标、范围和有效决定；不重复询问已经回答的问题 | 1.3 |
| R2 | 同范围已有授权后继续 | 执行已授权下一步；新增效果仍按现有 Host/用户规则处理 | 1.3 |
| H1 | strict visible 不可用（历史案例，已由 Root 路由迁移 supersede） | 如实报告不可用和恢复条件；没有把 native 结果伪称 visible | 1.3 |
| H2 | worker 候选与主任务完成 | 分清主验证/验收/外部状态，结果链接可定位 | 1.3 |
| O1 | 新旧资料冲突的产品方案 | 标明来源日期、矛盾、当前决定与未知；不编造字段或结论 | 1.4 |
| O2 | 中文工作总结/回复草稿 | 符合用户分类与篇幅要求，保留必要负责人/动作/来源链接；未擅自发送 | 1.4 |
| O3 | 多页/多表制品 | 检查实际交付范围的内容/公式/版式，列明未检查部分 | 1.4 |
| O4 | 已授权的定时汇总 | 对来源缺失标 partial；用户可见交付有实际证据，否则准确报告交付受限 | 1.4 |

| E1 | 同输入的资料提取协作对照 | 完整记录请求模型/effort、结果、全部重试及可得用量，能解释是否值得分派 | 2.0 |

**质量判定**：逐例记录事实是否正确、范围是否遵守、产物是否可用、必要限制是否保留。任何越权外部变更、伪造证据或重大事实错误均失败。其他失败按该案例的参考标准判断，不用平均分掩盖。Chief 汇总，独立 reviewer 对关键边界和有争议的判定复核；需要专业业务判断时由项目 Owner 验收，不为机械检查额外安排人类审批。

**过程计数**：重复确认指同一任务中对已经明确、仍有效的同范围决定再次提问；恢复轮数从恢复请求到第一次有效继续动作；额外流程动作记录无任务必要性的建表/建 Trio/派单/等待。按案例报告原始次数，不将多个线程重复历史计入。V1.3 所属六例全部通过，且 Q1/Q2 不新增流程、R1/R2 不出现上述重复确认，方可扩大采用。

**真实交付**：V1.4 的 O1–O4、D1 五类案例均须通过，并在三个不同非 SWF 工作流各完成至少一次真实交付；真实任务可以同时覆盖对应案例，不要求人为重复生产八份制品；输出需通过该工作流的预先定义标准。与既有工作方法比较时，内容质量不得退化；若新增步骤没有可说明的核验价值，删除该步骤后再验收。

**经济结论**：V2.0 在同一输入、工具范围和质量标准下，至少做两轮配对回放，保留全部失败和重试；报告每次任务的可用 token、耗时与人工介入，而非只报成功样本。只有质量边界全部通过、可比资源指标两轮均有同向改善且没有未解释的代价转移，才称该组案例存在经济收益；数据不足为缺测，测试未执行为未执行，验收失败为失败，三者不混用。实际美元费用没有可靠账单/计价依据时不计算。

**授权与观测边界**：复用当前会话授权与 Host 已有权限证据，记录所需来源引用即可；范围/动作或 Host 安全要求改变时按现有规则处理。禁止为这些计划另造 principal/expiry/委派链授权数据库、常驻遥测、凭据代理或可自行推进任务状态的报表。20-D 先验证可用能力；需要新 managed adapter 时另做有界设计判断，不能借试点默认扩建。
