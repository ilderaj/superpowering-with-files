# SWF 近 60 天审计与演进判断

**Chief 判断：SWF 应把主线放在跨任务、跨工具的可靠交付上。** 你的实际工作从业务资料、产品判断和设计方案，一直延伸到实现、审阅、发布和日常沟通。SWF 最值得保留的能力是：保存必要上下文，继承有效决定与授权，约束协作范围，说明证据能证明什么，并让结果真正可用。未来投入应以这些工作能否更顺利完成来衡量。

本轮产品判断的适用范围是你作为 Owner 的实际工作及当前工作区的复用价值；这份个人历史审计不能证明一般市场需求或其他用户的普遍收益。若以后对外推广，需要另用其他真实用户和使用场景验证。

建议按 **V1.3 可靠完成 → V1.4 跨域交付 → V2.0 经济协作与可验证演进** 推进。[完整版本计划](roadmap.md) 包含 12 个 Epic、依赖、验收案例、迁移与回滚。它们是待实施方案；本轮完成的是研究与规划，没有把未来收益写成已验证结果。

## 审计覆盖与可信度

冻结窗口：北京时间 **2026-07-08 13:50:37—2026-09-06 13:50:37**。扫描本机活动、归档和分页历史中的 3,970 个 JSONL 文件，合并 8 个续接别名后得到 **1,216 个逻辑会话：SWF 495，其他项目 721**。其中 813 个原生子代理会话，403 个顶层会话；顶层也含可见派单，不能全部当成人工独立任务。

规划侧覆盖 **242 组 Trio、726 个文件**：active 26 组，archive 216 组。全部建立内容索引；77 组带窗口日期的任务进行了三文件全文研读，其余 165 组用于日期边界与历史背景排查。会话侧逐项审阅分片索引及可用请求/结果摘要，再对关键用户纠正、转折和冲突原文深读，去重共 46 个会话；65 个用户引用锚点另行核验。具体名单、去重和缺失摘要说明见 [覆盖说明](coverage.md)、[会话登记](session-register.csv) 与 [规划登记](planning-register.csv)。

这里的「全面」是本地可获得材料的全量普查与分层研究，**不等于逐字语义阅读全部日志**。远端未同步、已永久删除及其他设备的历史不在可证明范围。历史助手声称的发布、测试通过和外部系统状态，也未在本轮逐一实时复验。

## 工作方法、偏好及其变化

我的归纳是：**先弄清事实与范围，形成可审阅结果，再沿已选方向推进，最后核对实际交付。** 这是从跨项目请求抽出的工作方式，不应变成每个小问题都要走的固定六步流程。

| 可跨项目复用的偏好 | 历史依据与适用边界 |
| --- | --- |
| 直接问题直接回答，正式工作再持久化 | 7 月已明确要求简单答案、确认真实问题、先脑暴；不能因已有 Trio 就把所有问题绑定进去。S01、S04、S05、S16 |
| 自主推进，但严格沿用范围 | 需要时先 review/先方案；明确授权后继续做。一次任务中的「先别实施」与另一任务中的「执行」各自有效，不能选一个永久套用。B03、P10、P20、S22 |
| 重视经济性，愿意使用协作 | 7 月已担心 Chief-worker 消耗，并反对写死模型等级；资料量与判断难度应分开。S02、S03、S12 |
| 要可见、可追溯的协作，也接受原生能力 | 历史上对 tracked 工作偏好 visible；8 月主动比较 native 的优势。本轮明确允许子代理。冻结的 strict-visible 任务仍应遵守原边界。S08—S10、S17 |
| 中文短、自然、能直接给人看 | 业务进展、产品方案及文档修订都有直接纠正；准确字段与必要技术标识仍应保留。B03、B09、B19、P09、P11、P12 |
| 工具服从任务，接受删减与退役 | Superpowers 不再默认、暂不采用某些上游能力、移除难用工具，都体现按实际价值选择。不能由此推断永久拒绝某类工具。S11、S19、P18 |
| 结果与证据要分层 | 候选、集成、实际运行和可见交付不能互相替代；业务分析同样保留上游、处理、报送等层次。B11、B12、规划证据 T09—T15 |

表中编号可在 [来源登记](sources.md) 定位原始消息。地区、定价、MVP 收费、特定浏览器等单项目决定没有提升为全局偏好。注入模板、worker 派单和助手自述也没有作为用户偏好的直接证据。

**本次模型选择的纠正**：最初研究分工继承 Astra，没有为低复杂度的提取任务单独选择模型，这是我的经济性判断疏漏。补跑的四个历史研究助手与一个审阅助手均显式请求 `main/gpt-5.6-luna`、`high`；脚本负责遍历、去重和机械核验，Chief 负责综合与冲突裁决。Luna + high 作为你当前指定的起点执行。配置记录不等于底层模型认证或费用账单，本轮不宣称已实现某个节省百分比。

## 当前项目：值得保留什么，优先补什么

基线为当前仓库 `2ecdfc9bf99cbce4e9a128d613a78fe8ae150c42`、包版本 1.2.0；本地另有先前 show-me 采用及无关未提交改动。以下是源码与文档检查结论，未把历史测试报告当作本轮测试结果。

**值得保留的基础**：三文件绑定与生命周期已经有实现；直接工作与委派工作有不同完成责任；投影有所有权保护、条件写入和补偿；可选技能的采用与分发有现成接缝。它们适合继续承载轻量的恢复与证据约束。应优先复用这些能力。[读取/绑定](../../../harness/trio/core/read.mjs#L431)、[状态存储](../../../harness/trio/core/store.mjs#L934)、[投影](../../../harness/trio/projection.mjs#L345)。

| 发现 | 证据与意义 | 优先处置 |
| --- | --- | --- |
| 产品定位与旧规划没有同步 | README 覆盖一般工作，PRODUCT 仍偏 coding/网站；旧 roadmap 仍列 1.0.11/1.0.12 planned。容易将已解决问题再次规划 | V1.3 对齐声明及旧条目去向，不为了旧文案造功能 |
| CLI 描述与行为有差异 | harness 帮助称 Trio 为 read-only，但有写操作；verify 帮助称输出目录，而当前主路径输出 stdout | V1.3 用实际命令核对用户能做什么 |
| 完成与交付的证明范围不够直观 | store 的 close 限制、直接任务完成、Host 动作和用户收到结果不是同一事件 | V1.3 给清楚的结果链接、剩余项与证据限制 |
| 办公能力的验证覆盖有限 | office contract 存在；现有制品验证使用固定样本及首屏图，不能证明任意多页文档质量 | V1.4 在实际业务制品上验证内容与完整交付范围 |
| 模型选择与可观测成本还需衔接 | API 有模型请求接缝，CLI next 未暴露相应参数；提示字节缩减及少量回放不证明端到端节省 | V2.0 对齐可用入口，比较质量、全部重试和可靠资源数据 |
| 包装兼容与执行能力不同 | generic/分发接缝存在，不代表每个 Host 已能真实执行；身份/权限认证依赖 Host | 仅做有需求的单一外扩试点，分层说明可证明能力 |

具体源码定位见 [实现依据](sources.md#当前实现依据)。routing/store 文件较大只是维护线索，没有足够证据支持再来一次全面架构重写。受控投影也不应宣传为覆盖所有外部目标的全局原子事务。

## 演进选择及优先级依据

我建议把 SWF 的目标写成：**让复杂工作在中断、换工具或协作之后，仍能沿着有效决定，以合理成本交付可验证结果；简单工作保持简单。** 这是本轮建议的产品目标，不是已经修改过的官方定位。

1. **V1.3 可靠完成。** 先解决入口、恢复、收尾与证据说明的矛盾。理由是这些问题影响所有工作域，而且已有实现可复用；可通过明确任务案例验证，不需要先扩大架构。
2. **V1.4 跨域交付。** 把跨来源产品方案、日常工作总结、设计到实现交接作为三个试点。理由是它们直接来自你的实际工作，能检验 SWF 是否超出自我维护产生价值；采用按需方法，领域知识保留在原项目。
3. **V2.0 经济协作与可验证演进。** 建立协作与技能的采用/退役依据，比较 Host 原生与 SWF 方法，观测失败重试和可得成本。理由是经济性是持续需求，但当前缺少可支持普遍收益宣传的对照数据。

这些是顺序依赖的三个大型迭代，每个都能在不完成下一版时独立交付。经济分派原则从本轮立即执行，不需要等 V2.0；V2.0 承载的是可重复的验证和产品化。最先切入 **13-A 契约对齐 + 13-D 真实工作基线**，随后改善恢复/交付。详细计划给出 12 个初始案例和明确失败条件，不虚构日期、吞吐量或 token 总预算。

当前不建议投入：全量多 Host 扩张、常驻 agent 调度器、第二套授权/任务数据库、支付领域知识内置、全量私人会话长期索引、以角色或技能数量为目标的扩展。以后有具体缺口时再作有界判断。
