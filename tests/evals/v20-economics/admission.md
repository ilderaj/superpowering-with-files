# 实验派单预检

本流程只用于 V2.0 eval 的证据准备，不新增 Host runner、worker 契约、路由或权限能力。任务状态仍由原 Trio 管理。当前 Host 无法在创建 native worker 前返回该 worker 的完整继承上下文；不得声称已实现 pre-model admission。

## 两个读取范围

- 启动输入：逐文件列出确有需要的 AGENTS、Trio/dev、绑定 Trio 及 memory registry，保存绝对路径、真实路径和 SHA-256。两组使用相同的启动清单；不能以「全部全局目录」代替清单。注入的 Host instructions 单独留证，不把用户清单当成可覆盖它们的权限。
- 业务输入：仅列出本槽 case、方法、工具约束和 scratch。不同槽写目录必须互斥。rubric、其他槽输出和旧实验始终不在业务读取范围内。

启动指令要求读取清单外的文件时，遵守 Host 指令优先级，报告冲突并停在启动阶段；不要为了保持实验通过而隐藏该读取，也不要继续业务工作。可选记忆仅在 Host 条件适用时使用；自包含任务无需历史时可跳过。启动阶段允许读取的内容也必须记入成本与上下文证据，不能在报告中默默扣除。

## 创建前：Chief 静态检查

1. 使用现有工具核对模型能力与用户选择；冻结 model、effort、预期 approval policy、Host 暴露的 sandbox 及其限制。请求值不是实际认证。
2. 在唯一证据目录记录两份清单、文件 hash、绑定 Trio hash、两阶段指令、业务完成判据、超时与失败保留规则。不得修改先前 cohort。
3. 检查文件存在、真实路径、scratch 互斥与 runtime。已知无法满足的条件在派单前阻止业务实验。完整继承上下文仍未知，只能称静态准备完成。

## 创建后：先启动，后业务

1. 创建同一 worker 的启动阶段，指令只要求检查启动清单并返回 receipt，不给业务执行许可。不得读取业务输入或 rubric。若无法遵守则报告冲突；不替换成一个新 worker 掩盖失败。
2. Chief 读取该精确 worker 的 Host rollout，核对实际 model/effort/approval、注入的 memory/AGENTS/skill 规则、完整工具轨迹和启动 receipt。验证声明的文件 hash 未变，业务尚未读取/写入。逐条记录不满足项；worker 自述不能代替检查。
3. 仅当该 worker 的启动证据通过，Chief 向同一 worker 发送冻结的业务指令；不重启、不新建替代。若需要清单外读取，在业务前停止，修改未来试验的协议，保留本次失败。
4. 业务结束后核对实际读写轨迹、输入 hash 和结果。启动通过不是业务通过；两者都不是正式版本验收。Full Access 下此流程属于检查与停机约定，不是文件系统隔离或安全防护。

## 小规模验证与正式实验的边界

先运行两个相同配置的微型 probe，验证启动 receipt → Chief 核验 → 同 worker 业务执行的完整路径。两者成功只证明该 Host 配置下预检流程可行，不证明经济收益或所有正式槽都可执行。正式 cohort 的每个槽仍须逐一预检；未来 cohort 必须事前冻结两阶段生命周期、双方相同的启动清单及所有成本窗口，并使用新的独立 holdout。

主指标窗口必须包含该槽启动与业务阶段；不能从业务放行后才开始计量。父任务核验、派单和评审另记共享成本，未知不填零。任意失败、超时、额外读取、重试和配置漂移均保留；不得从成组统计中静默丢弃。被阻止的正式槽保留未执行/失败事实；先以 Chief 记录裁定状态，不能把「未跑」当作成功。

本轮最多两个 probe 和一次有界独立审查，完成后在 Trio 记录可行/受阻及后续决定，不自动触发完整 16 槽。DSH、visible-worker 旧桥、全局 policy 修改、reset、release 和 adoption 均不在此流程内。
